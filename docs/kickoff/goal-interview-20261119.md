# 万象（OneX）立项目标访谈记录

日期：2026-11-19。方式：通过逐轮提问厘清目标。本文记录问题、用户的回答，以及访谈过程中提出、尚待确认的判断。第五轮问题尚未回答，在新会话中继续。

## 立项前提

- 万象的英文名是 OneX，是 SIMA PoC 的后继正式项目。
- SIMA 只作参考，代码从头写起，不迁入 SIMA 的代码。
- 技术栈沿用 SIMA：Server 用 Bun/TypeScript/Hono，Edge 用 Rust/Tokio。数据仓库重新考虑，包括关系库、时序库、状态库和对象库。
- 允许推送到本仓库的 `main`。

## 第一轮：为谁做、为什么做

| 问题 | 回答 |
| --- | --- |
| 第一个真实用户是谁 | 一到两家外部企业，之后会有很多。规模不定：有 10 人左右的，也有 50 人以上的，甚至更大 |
| 只能交付一样东西的话选什么 | 纳管与统一管控。先定大计划，再多轮冲刺，每轮跑一个小 PoC |
| SIMA 最不满意的是什么 | Server 性能太差，对话一多，监察就没法看。Edge 不稳定，要测很多次才能流畅对话，跟 Magpie 没法比 |
| 万象里的“硅”是什么 | 硅就是各种 Agent。万象是基座，是 AI infra，就是 bus |
| 数据层为什么要重做 | 多租户分库，加上大量人机对话回流到 Server 备查，会带来大并发。部署形态是 SaaS |

## 第二轮：管控管什么、看什么

| 问题 | 回答 |
| --- | --- |
| 企业为什么付钱 | 首先要好用：支持很多家 Agent，一步就能用起来，没有技术门槛。其次是工作内容和 token 费用透明可见 |
| 监察看汇总还是看全文 | 取决于老板当时的目的，两者并列，不分开 |
| Edge 输给 Magpie 的是什么 | 只能看到现象：SIMA Edge 打了太多补丁，代码复杂度太高，导致登录、对话中断、配置同步等问题互相纠缠，还不能远程调试或回传日志。之前还把模型 API 调用拉到 Server 中继，链路过长，更不稳定。Edge 必须拦截模型流量 |
| 第一版支持哪些 Agent | CLI：Claude Code、Codex、Kimi。桌面：WorkBuddy、DeepSeek Harness Desktop |
| 数据规模和归属 | 每人每天约 2000 万至 3000 万 token，会话最多约 40 至 50 轮。对话必须完整回传。客户能否接受由数据保密协议决定 |
| 团队 | 开发只有用户一人，另有一名测试配合。运维还在招人，目前由用户和 Agent 一起维护。所以万象自身必须对 AI 友好：接口方便 Agent 操作，远端甚至可以通过 Server 和 Agent 连起来配合测试 |

访谈中提出、待确认的判断：

- 每次请求都会重发完整上下文，所以 token 量远大于需要存储的新增内容。回流单位应是增量会话事件，token 用量作为计量数据单独记录。
- “AI 友好”应作为第一设计原则：所有状态可经 API 查询，所有操作可由 Agent 执行，每台 Edge 可远程诊断并回传日志。

## 第三轮：边界与节奏

| 问题 | 回答 |
| --- | --- |
| 一步用起来指什么 | 安装并登录 OneX Desktop，自动获得 AI 能力配置，点击要用的 Agent 即可一键启动。Agent 只能由 OneX 下载、由 OneX 启动，外部启动的 Agent 不受管理 |
| 模型额度从哪里来 | 统一采购。租户向 OneX 购买“橡皮”（内部积分的昵称）。客户自带的密钥无法纳管，目前不考虑。第一版就要有账户，Provider 的计价或计分要有折扣（倍数）对齐 |
| Agent 的先后 | 5 个 Agent 的纳管可以利旧，SIMA 在接管各 Agent 上积累的东西有价值 |
| c-si-bus 在第一版的位置 | 先做纳管。第一版保证可用和稳定，分发和协作以后再展开 |
| 第一轮冲刺的成功标准 | 一名新员工在一台干净的 Mac 上，5 分钟内装好并登录，用 Claude Code 连续工作 2 小时不掉线、不重新登录。管理员在网页上实时看到完整对话和 token 费用。出故障时，Agent 能通过 API 拉取这台 Edge 的日志。要合理利旧 SIMA，但 SIMA Server 的页面只有“监察”和“Agent”两块还说得过去，其他页面是运维地狱 |
| 明确不做 | 不做私有化部署。待展开：Linux 桌面、内部 Agent 互相委托、应用市场 |

访谈中提出、待确认的判断：

- 利旧的是知识，不是代码。把 SIMA 里每个 Agent 的接管细节整理成适配规格，包括版本、配置路径、启动参数、会话格式和已知的坑，再按规格干净地重写。

## 第四轮：账户、架构和角色

| 问题 | 回答 |
| --- | --- |
| 橡皮规则 | 预付费，余额用完立即中断。租户可以把额度分到组和个人，也可以选择不限制。倍率按模型定，输入和输出分开计价。由管理员手工加分 |
| 云端网关 | 重点考察学习 Magpie：本地路由，从服务端拉取配置同步。云端网关目前不需要 OneX 自己做，Edge 就地分发更快。上游有 Kimi 这类官网 Code Plan，也有按量计价的 OpenRouter |
| Desktop 形态 | 带托盘、可隐藏的 Desktop，后台有 daemon。Mac 和 Windows 都要：开发机是 Mac，测试员用 Windows |
| 角色 | 要有组管，现在的租户就是分层管理的 |
| 隐私与审计 | 户主可以决定给管理员、组管开放哪些可见范围，户主自己全部可见。对话会被查看，在安装时就签约，不需要每次登录告知。审计必须记录，这是隐私安全的最后防线 |

## Magpie 初步考察

参考仓库：<https://github.com/yetone/magpie>，MIT 许可，Go 语言，约 62 万行。查看的提交是 `0e3d093611e8bd226e3136113aafd75f5d7f4914`（2026-11-19）。

- 定位是单人工具。本地网关 `127.0.0.1:3425` 支持 OpenAI Chat、OpenAI Responses、Anthropic Messages 和 Gemini 四种协议，并在它们之间互相转换。支持约 90 个 Agent，其中包括 WorkBuddy、DeepSeek Harness 和 Kimi Code。
- 配置同步（`internal/davsync`）是同一个人在自己几台电脑之间同步，用口令加密后存到 WebDAV、S3 或 GitHub，不涉及管理员向员工下发。
- 用量记录（`internal/usage`）写在本机的 JSON lines 文件里，默认不离开本机，只有开启 OTLP 导出后才会外发。
- `internal/lastgood` 的做法：状态文件写坏时回退到上一个好版本，绝不把“读不出来”当作“空”。
- Agent 配置原子改写，保留注释和格式，卸载时恢复原样。
- `LESSONS.md` 记录了一套由 Agent 编写、审查、合并、发布代码的工作方式，每晚复盘，把重复出现的错误沉淀成规则。

访谈中提出、待确认的判断：

- Magpie 的密钥和费用都属于用户本人，本地路由没有信任问题。OneX 是公司付费、员工使用，照搬会有两个风险：上游密钥要下发到员工电脑；计费和断流都依赖 Edge 自己上报。
- 不做云端网关也可以缓解：上游如果支持子密钥加额度上限（例如 OpenRouter 的 Provisioning API），就可以给每个租户或每个人发独立子密钥，限额、可吊销，并用上游账单核对 Edge 上报的用量。Kimi Code Plan 的凭据发放方式待确认。

## 第五轮：待回答

1. **密钥风险接受到什么程度？** A：接受上游子密钥下发到 Edge，由额度上限、吊销和账单核对兜底。B：密钥绝不落到员工电脑，必须有一层很薄的云端转发。Kimi Code Plan 的凭据是怎么发放的？
2. **Edge 用 Rust 重写，还是基于 Magpie 的 Go 代码 fork？** Fork 的好处是 Agent 适配和协议转换已经成熟，代价是代码量大、技术栈要换成 Go、难以跟进上游。
3. **离线怎么办？** Edge 与 Server 断开时，员工能否继续工作、能工作多久？候选方案：在本地缓存一个短时额度租约（例如 10 分钟），过期就停止，对话记录先存本地，恢复后补传。
4. **第一个租户的上线日期？** 有没有外部客户已经在等的时间点？
