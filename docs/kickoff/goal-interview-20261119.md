# 万象（OneX）立项目标访谈记录

日期：2026-11-19。方式：通过逐轮提问厘清目标。本文记录问题、用户的回答，以及访谈过程中提出、尚待确认的判断。访谈共八轮，已结束。

## 立项前提

- 万象的英文名是 OneX，是 SIMA PoC 的后继正式项目。
- SIMA 只作参考，代码从头写起，不迁入 SIMA 的代码。
- 技术栈沿用 SIMA：Server 用 Bun/TypeScript/Hono，Edge 用 Rust/Tokio。数据仓库重新考虑，包括关系库、时序库、状态库和对象库。
- 允许推送到本仓库的 `main`。

## 第一轮：为谁做、为什么做

| 问题 | 回答 |
| --- | --- |
| 第一个真实用户是谁 | 一到两家外部企业，之后会有很多。规模不定：有 10 人左右的，也有 50 人以上的，甚至更大 |
| 只能交付一样东西的话选什么 | 纳管与统一管控。先定大计划，再多轮冲刺，每轮跑一个小 PoC |
| SIMA 最不满意的是什么 | Server 性能太差，对话一多，监察就没法看。Edge 不稳定，要测很多次才能流畅对话，跟 Magpie 没法比 |
| 万象里的“硅”是什么 | 硅就是各种 Agent。万象是基座，是 AI infra，就是 bus |
| 数据层为什么要重做 | 多租户分库，加上大量人机对话回流到 Server 备查，会带来大并发。部署形态是 SaaS |

## 第二轮：管控管什么、看什么

| 问题 | 回答 |
| --- | --- |
| 企业为什么付钱 | 首先要好用：支持很多家 Agent，一步就能用起来，没有技术门槛。其次是工作内容和 token 费用透明可见 |
| 监察看汇总还是看全文 | 取决于老板当时的目的，两者并列，不分开 |
| Edge 输给 Magpie 的是什么 | 只能看到现象：SIMA Edge 打了太多补丁，代码复杂度太高，导致登录、对话中断、配置同步等问题互相纠缠，还不能远程调试或回传日志。之前还把模型 API 调用拉到 Server 中继，链路过长，更不稳定。Edge 必须拦截模型流量 |
| 第一版支持哪些 Agent | CLI：Claude Code、Codex、Kimi。桌面：WorkBuddy、DeepSeek Harness Desktop |
| 数据规模和归属 | 每人每天约 2000 万至 3000 万 token，会话最多约 40 至 50 轮。对话必须完整回传。客户能否接受由数据保密协议决定 |
| 团队 | 开发只有用户一人，另有一名测试配合。运维还在招人，目前由用户和 Agent 一起维护。所以万象自身必须对 AI 友好：接口方便 Agent 操作，远端甚至可以通过 Server 和 Agent 连起来配合测试 |

访谈中提出、待确认的判断：

- 每次请求都会重发完整上下文，所以 token 量远大于需要存储的新增内容。回流单位应是增量会话事件，token 用量作为计量数据单独记录。
- “AI 友好”应作为第一设计原则：所有状态可经 API 查询，所有操作可由 Agent 执行，每台 Edge 可远程诊断并回传日志。

## 第三轮：边界与节奏

| 问题 | 回答 |
| --- | --- |
| 一步用起来指什么 | 安装并登录 OneX Desktop，自动获得 AI 能力配置，点击要用的 Agent 即可一键启动。Agent 只能由 OneX 下载、由 OneX 启动，外部启动的 Agent 不受管理 |
| 模型额度从哪里来 | 统一采购。租户向 OneX 购买“橡皮”（内部积分的昵称）。客户自带的密钥无法纳管，目前不考虑。第一版就要有账户，Provider 的计价或计分要有折扣（倍数）对齐 |
| Agent 的先后 | 5 个 Agent 的纳管可以利旧，SIMA 在接管各 Agent 上积累的东西有价值 |
| c-si-bus 在第一版的位置 | 先做纳管。第一版保证可用和稳定，分发和协作以后再展开 |
| 第一轮冲刺的成功标准 | 一名新员工在一台干净的 Mac 上，5 分钟内装好并登录，用 Claude Code 连续工作 2 小时不掉线、不重新登录。管理员在网页上实时看到完整对话和 token 费用。出故障时，Agent 能通过 API 拉取这台 Edge 的日志。要合理利旧 SIMA，但 SIMA Server 的页面只有“监察”和“Agent”两块还说得过去，其他页面是运维地狱 |
| 明确不做 | 不做私有化部署。待展开：Linux 桌面、内部 Agent 互相委托、应用市场 |

访谈中提出、待确认的判断：

- 利旧的是知识，不是代码。把 SIMA 里每个 Agent 的接管细节整理成适配规格，包括版本、配置路径、启动参数、会话格式和已知的坑，再按规格干净地重写。

## 第四轮：账户、架构和角色

| 问题 | 回答 |
| --- | --- |
| 橡皮规则 | 预付费，余额用完立即中断。租户可以把额度分到组和个人，也可以选择不限制。倍率按模型定，输入和输出分开计价。由管理员手工加分 |
| 云端网关 | 重点考察学习 Magpie：本地路由，从服务端拉取配置同步。云端网关目前不需要 OneX 自己做，Edge 就地分发更快。上游有 Kimi 这类官网 Code Plan，也有按量计价的 OpenRouter |
| Desktop 形态 | 带托盘、可隐藏的 Desktop，后台有 daemon。Mac 和 Windows 都要：开发机是 Mac，测试员用 Windows |
| 角色 | 要有组管，现在的租户就是分层管理的 |
| 隐私与审计 | 户主可以决定给管理员、组管开放哪些可见范围，户主自己全部可见。对话会被查看，在安装时就签约，不需要每次登录告知。审计必须记录，这是隐私安全的最后防线 |

## Magpie 初步考察

参考仓库：<https://github.com/yetone/magpie>，MIT 许可，Go 语言，约 62 万行。查看的提交是 `0e3d093611e8bd226e3136113aafd75f5d7f4914`（2026-11-19）。

- 定位是单人工具。本地网关 `127.0.0.1:3425` 支持 OpenAI Chat、OpenAI Responses、Anthropic Messages 和 Gemini 四种协议，并在它们之间互相转换。支持约 90 个 Agent，其中包括 WorkBuddy、DeepSeek Harness 和 Kimi Code。
- 配置同步（`internal/davsync`）是同一个人在自己几台电脑之间同步，用口令加密后存到 WebDAV、S3 或 GitHub，不涉及管理员向员工下发。
- 用量记录（`internal/usage`）写在本机的 JSON lines 文件里，默认不离开本机，只有开启 OTLP 导出后才会外发。
- `internal/lastgood` 的做法：状态文件写坏时回退到上一个好版本，绝不把“读不出来”当作“空”。
- Agent 配置原子改写，保留注释和格式，卸载时恢复原样。
- `LESSONS.md` 记录了一套由 Agent 编写、审查、合并、发布代码的工作方式，每晚复盘，把重复出现的错误沉淀成规则。

访谈中提出、待确认的判断：

- Magpie 的密钥和费用都属于用户本人，本地路由没有信任问题。OneX 是公司付费、员工使用，照搬会有两个风险：上游密钥要下发到员工电脑；计费和断流都依赖 Edge 自己上报。
- 不做云端网关也可以缓解：上游如果支持子密钥加额度上限（例如 OpenRouter 的 Provisioning API），就可以给每个租户或每个人发独立子密钥，限额、可吊销，并用上游账单核对 Edge 上报的用量。Kimi Code Plan 的凭据发放方式待确认。

## 第五轮：密钥、Edge 技术、离线和上线日期

| 问题 | 回答 |
| --- | --- |
| 密钥风险接受到什么程度 | Provider 密钥直接下发给 Edge 的 daemon。daemon 在本机代理转发到用户选择的模型路由，作用和 Magpie 一样，是一个本机 router |
| Edge 用 Rust 重写还是 fork Magpie | Rust 重写。把 Magpie 的协议转换和 Agent 适配当作规格参考，尽量覆盖 Magpie 支持的所有 Agent 和协议 |
| 离线怎么办 | 短时额度租约：本地缓存一个短时租约，过期就停止，对话记录先存本地，恢复后补传 |
| 第一个租户的上线日期 | 尚未确定 |

访谈中提出、待确认的判断：

- 密钥只放在 daemon 里，最好存进系统钥匙串（macOS Keychain、Windows Credential Manager），不写进任何 Agent 的配置文件。Agent 配置里只写 `127.0.0.1` 地址和一个本机令牌，这样员工从 Agent 配置里拿不到上游密钥。
- 下发的仍应尽量是子密钥，而不是租户的主密钥。否则一台电脑泄露，就会暴露整个上游账户。上游支持子密钥加额度上限的，按租户或按人发；不支持的（Kimi Code Plan 待查），记为已知风险。
- 租约同时有时间和额度两个上限，先到先停。这样余额最多被超支一个租约的额度。
- “覆盖 Magpie 的所有 Agent”是长期目标。适配层按规格驱动来设计，方便逐个添加；顺序是第一轮冲刺只做 Claude Code，然后补齐第一版的 5 个 Agent，其余按客户需求加入。

## 第六轮：Desktop、租户隔离和数据层

| 问题 | 回答 |
| --- | --- |
| Desktop 用什么写 | Tauri |
| 租户隔离到什么程度 | 每租户一个库。初期可以先用多个租户 SQLite 库加一个系统 SQLite 库做验证性开发 |
| 数据层怎么组合 | 再找更轻量的开源方案：多个 SQLite（Bun 内置）；对象存储用 RustFS 做 sidecar；分析库不用 ClickHouse，改用嵌入式 DuckDB；Redis 放在线状态、会话状态和租约 |
| 认可哪些待确认判断 | 认可：回流传增量；AI 友好为第一设计原则；利旧知识不利旧代码。密钥方面：渠道 API key 只会被 OneX Edge 的 daemon 使用，可以加密下发，租约期内即可调用 |

访谈中提出、待确认的判断：

- 加密下发保护的是传输和落盘。daemon 调用上游时密钥必须解密到内存，有本机管理员权限的员工仍能取出。租约只约束 daemon，约束不了取出后的密钥。所以上游支持子密钥的，仍建议按租户或按人发，泄露时只吊销一把；不支持的记为已知风险。
- SQLite 每个库只允许一个写者。会话回流是写多的负载，要用 WAL 模式，并由一个写入队列按租户批量提交。
- DuckDB 同样是单进程写。建议由 Server 定时把 SQLite 中的会话事件和计量数据导出为 Parquet，存进 RustFS，DuckDB 只负责读和分析，不承担在线写入。
- 待核实：DuckDB 的 Node 绑定在 Bun 下是否可用；RustFS 的许可和成熟度。

## 第七轮：子密钥、通信、登录和状态库

| 问题 | 回答 |
| --- | --- |
| 是否按租户或按人发子密钥 | 先简单来。服务端最终给每人配一个 provider，基本就相当于子密钥。现阶段只要 token 统计和配给能管住 |
| Edge 和 Server 怎么通信 | WebSocket，此前已确认 |
| 员工怎么登录 | 验证码和邀请码都支持。租户总人数受能力合约控制 |
| 状态库 | 用 Valkey。Server 会频繁更新，状态不能放进程内存，否则每次发版都会打断在线会话 |

访谈中提出、待确认的判断：

- 一条 WebSocket 长连接承载配置下发、租约续期、会话回流、断流指令和远程诊断。断线重连和回流补传要按序号做到不丢、不重。
- 能力合约的含义待确认：它是否就是租户购买的套餐，规定人数上限、可用 Agent 和可用模型？

## 第八轮：能力合约与 UI 规则

| 问题 | 回答 |
| --- | --- |
| 能力合约包含什么 | 参考 SIMA 现有内容。SIMA 的界面不对，但 SIMA 有 UI 设计规则，只是实现时没有遵守 |
| 访谈是否结束 | 由 Claude 判断是否已经详细理解 |

SIMA 中的出处（查看时间 2026-11-19，仓库 `/Users/HHH/Code/SA/SIMA`，主目录 HEAD `a8685e23`，线上实现在其他分支上）：

- 能力合约：`docs/plans/tenant-capability-contract-20261112.md`。管理链是“平台公共能力池和公共 Provider → 平台给租户配置合约 → 租户有效能力池 → 分配给组和成员 → 用户实际使用”。合约内容包括版本和生效状态、公共资源授权（Agent、MCP、Skill、Hook、Bot）、公共 Provider 和允许的模型、两个租户自主权开关（能否自接外部 Provider、能否上传租户共享 Tools）、可委派动作的上限、变更影响预览。
- 合约模板和 Token 配给：`docs/reports/s6-ui-analysis-20261114.md`。平台维护带版本的合约模板，租户合约可以组合多个模板，并确认最终的 Token 总额，再分配到组和成员。硬上限必须在模型消费入口执行：先预留，流式结束后按真实用量结算；用量缺失时标为待结算，不能当作零。
- UI 设计规则：`docs/plans/ui-consolidation-20261114.md` 的“三种页面模式”和“容器内展开与导航节制”两节，样机在 `docs/demos/sima-console-20261114/`。规则要点：页面只有台账、钻取、表单三种形态；钻取时原台账缩成左侧清单，详情在右侧展开；主表单不用对话框和遮罩；只有分类明确时才出现左侧菜单；大列表由服务端分页；桌面行高 32 至 40 px，按 1280×720 和 1440×900 验收。

访谈中提出、待确认的判断：

- OneX 第一版的能力合约取 SIMA 合约的子集：人数上限、可用 Agent、可用 Provider 和模型（含橡皮倍率）、橡皮总额及其向组和个人的分配。合约模板、多模板组合、MCP/Skill/Hook/Bot 分发、两个自主权开关、委派动作上限放到后续冲刺。理由是第一版只做纳管，客户自带密钥目前不考虑，自接 Provider 的开关在第一版没有用处。
- SIMA 的 UI 规则直接作为 OneX 管理端的规则，从第一个页面开始遵守，并写进验收标准，避免重复 SIMA“有规则但没照做”的问题。

## 访谈结论

目标、边界和主要技术选型已经清楚，访谈到此结束。以下事项不再通过访谈解决，作为计划中的核实任务：

- Kimi Code Plan 的凭据是怎么发放的，能否按人发放。
- DuckDB 的 Node 绑定在 Bun 下是否可用；RustFS 的许可和成熟度。
- 第一个租户的上线日期，等第一轮冲刺达标后再定。
